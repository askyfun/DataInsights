## 二、需求分析裁定（析客）

| # | 决策 | 结论 | 理由 |
|---|------|------|------|
| **C1** | TTL 形态 | **记录永不物理删除**，仅软过期。`expires_at` **单字段**判定，**不加 `status` 枚举** | 状态是 `expires_at` 的派生值，重复存储会漂移 |
| **C2** | "删除个人历史"的处置 | 取消删除，改「**从我视图中移除**」（localStorage，仅本机）。定位为**永久机制**。合规"彻底抹除"诉求 → **脱敏重写**（清空敏感值、**保留行**），**不删行** | 无账号体系下 `owner_id` 无值可填；任何记录都可能已被分享，真删会断链 |
| **C3** | 全员共享后的隐私缓解 | ① 历史列表**只展示元数据**，不展示条件值明细；② 敏感键筛选值截断 / 中段脱敏；③ 依赖 L0 内网 + 使用约定 | 原"需显式发布才可见"与 P-4 直接矛盾，整体废弃 |
| **C4** | 不真删的存储控制 | 单条 `spec_json` **上限 32KB**，超限拒存并友好提示；默认视图过滤过期 = 软归档 | 表单调增长需硬上限兜底 |
| **C5** | 记录表 vs 审计表：一张还是两张 | **本期仅建 1 张 `bi_query`**；语义上区分"配置资产 / 行为事件"，账号体系落地后再物理拆 `bi_audit_log` | 一期一张落地成本最低；用 `hit_count`/`last_accessed_at` 顶行为事件 |
| **C6** | `owner_id` / `tenant_id` 是否保留 | **保留（nullable）**，**推翻数析的删除主张** | R-22 已把"新实体落库即带 owner"定为**不可逆埋点**；新表独缺会成为唯一缺口，多租户上线后历史无法归属 |
| **C7** | 是否保留"保存为图表"链路 | **保留**（另存为图表 → `/charts` → 可生成 `/share/:token`） | 现有 `/charts`、`/shares`、`/share/:token` 全依赖它；URL 分享是临时、图表是可复用资产 |
| **C8** | 分享动作的产品形态 | 地址栏 + 显式「复制链接」按钮**两者都要**；地址栏是唯一真相源，按钮只是便捷动作 + 埋点 | 不引入第二套状态 |
| **C9** | 撤销 / 重做 / 重置是否本期做 | **本期做**（R-32，瑞思列为必备"每步可回退"） | 试错是主场景 |
| **C10** | 记录状态机的默认覆盖行为 | **禁止默认覆盖**；提供「更新当前 / 另存为新 / 重命名」 | 默认覆盖会让**已分享链接被静默改写**，是明确投诉源 |

## 三、技术裁定（主理人 + 工程实现期）

| # | 决策 | 结论 | 触发原因 |
|---|------|------|----------|
| **T-1** | 是否可用部分索引加速"未过期记录" | **禁止**。PostgreSQL 部分索引谓词必须 **IMMUTABLE**，`now()` 是 **STABLE** → `WHERE expires_at > now()` 会被 PG 直接拒绝（`functions in index predicate must be marked IMMUTABLE`）。**改用普通复合索引** `(created_at DESC, query_id)`，过期判定降为扫描后 filter | 数析原建议 `WHERE status='active'` **根本建不出来**（且与 C1 冲突） |
| **T-2** | 默认参数一致性 | 新增配置约束 **`TTL 下限 ≥ 默认视图窗口`** | 析客 TTL 90 天 > 数析视图窗口 30 天 → **默认路径上"过滤过期"是空操作**（命中零条），数析的性能担忧偏悲观 |
| **T-3** | "最短见价值"的口径 | **拆为两个度量**：分享闭环（不含 R-44）与 历史列表可用 | 历史列表**不是分享的前置**，路径原口径把两者混算 |
| **T-4** | 落库触发策略 | **内容 hash 去重 upsert + 异步写入 + 显式动作强制 flush** | 每次执行落库 2500 行/天且同步写入会顶破首屏 P95 ≤1.5s；hash 去重后 ≈1000 行/天 |
| **T-5** | 异步写入的实现方式 | **进程内有界队列（buffered channel）+ goroutine worker 池**，队列满**同步兜底**（不静默丢） | 全仓无 Redis / asynq / cron 基建，不引外部依赖 |
| **T-6** | 是否引入后台清理定时任务 | **禁止** | 无定时任务基建；改读时惰性判定（后续进一步改为纯软过期，不写） |
| **T-7** | queryId 的 id 形态 | **不可猜 UUID v4**，明确否掉 DataWind 的 8 位自增数字 | 自增可枚举 + 无鉴权 = **全库查询历史任人遍历** |
| **T-8** | 软删除的级联实现 | **显式级联、同一事务**；级联子查询**故意不带** `deleted_at IS NULL` | 改软删后 `ON DELETE CASCADE` 不再触发；若子查询加上过滤会**级联断链**（刚软删的父行查不到） |
| **T-9** | 级联与 `Update` 的边界 | 整行 UPDATE 需 `.ExcludeColumn("deleted_at")`，防止零值 `sql.NullTime` 把已删行**误复活** | bun v1.2.16 的 `nullzero` 仅影响 INSERT、不影响 UPDATE |
| **T-10** | 软删除的索引键 | partial 索引谓词 `WHERE deleted_at IS NULL` **合法**（`IS NULL` 是 IMMUTABLE），但索引**键不能是 `deleted_at`**（满足谓词的行该列恒为 NULL、索引键是常量）→ 键改为真实查询列 `id` / `(datasource_id,id)` / `(dataset_id,id)` / `chart_id` | 实现期审计发现（`0f8d10c`） |
| **T-11** | `bi_share.expires_at` 的语义 | **不变**——用户显式设定的过期仍然生效；与"系统清理导致链接失效"是两回事 | 避免把"不真删"误读为"链接永不过期" |
| **T-12** | `deleted_at` 是否出现在 API 响应 | **不暴露**（`json:"-"`） | 前端零改动 |
| **T-13** | 是否建回收站 / 恢复接口 | **不建**（本期只做"不真删"，不做"能找回"的 UI） | 数据在库，恢复能力以后随时可加 |
| **T-14** | 记录表名 | **`bi_query`**（数析原提议 `bi_query_log`，采纳其改名） | 语义已从"日志"变为"配置资产 + 轻量留痕" |
| **T-15** | 编号纪律 | **沿用旧编号、只给新条目新编号**；汇编前必须做**编号一致性校验** | 三次同型撞车（析客与路径各自从 R-30 / R-44 起编号但含义不同），`R-30'` / `R-40`（重写）为归一化结果 |

## 📌 TL;DR（执行摘要）
- **机制整体切换**：由 v1 的「URL 携带压缩状态（客户端编码）」→ v2 的「**查询落库 + queryId 寻址 + 地址栏 id 化 + 历史查询列表**」（服务端持久化）。v1 的 `lz-string` 编码、URL <2000 硬约束、超长报错、R-35 可追溯 opt-in **全部作废**。
- **抄火山的**：id 寻址 · 地址栏即分享入口 · 查询可回溯。**不抄的**：8 位自增数字 id（可枚举 + Data Insights 无鉴权 = 全库查询历史任人遍历）→ 换**不可猜 UUID**；"每次查询无限落库" → 降级为 **hash 去重 upsert + TTL**；**不引入后台定时清理**（无 redis/asynq/cron 基建）。
- **可追溯性翻转为默认**：每次查询本就落库（含 ip / created_at / dataset / chart）→ R-08 简化为"落库即留痕"，v1 的"降级为 opt-in"作废。
- **写放大是首要风险**：假设 50 用户 × 人均建图 5 次/天 × 10 次查询 → 2500 次/天，去重后 ≈1000 行/天。**同步落库会顶破首屏热 P95 ≤1.5s**，必须**异步 + hash 去重 + 显式动作 flush**。
- **代价（要知情）**：服务端持久化比客户端编码**更重**。当期 91–131 → **98–146 人日**；最短见价值路径 15–24 → **18–29 人日**（服务端落库成为分享的前置）。
- **一个需你拍板的开放决策**：无账号体系下，历史查询列表默认**全员可见**还是**仅本人可见**（瑞思判定全员可见会成为投诉源）。

## 二、机制定义与对标杆

### 2.1 与火山 DataWind 的对齐 / 偏离（竞析取证，官方文档实证）

| 维度 | DataWind 实际做法（文档实证） | Data Insights v2 裁定 |
|------|------------------------------|-----------------|
| queryId 形态 | **8 位纯数字**（示例 `98850742`），自增/雪花 | ❌ 不抄 → **不可猜 UUID v4**（可枚举 + 无鉴权 = 全库历史任人遍历） |
| 地址栏形态 | `#/dataQuery?appId=&id=<queryId>&rid=&sid=`，queryId 在**参数** `id` | ✅ 抄结构 → `/chart-builder?q=<uuid>` |
| 地址栏即分享入口 | ✅（因此**右上角没有分享按钮**——与 v1"无分享按钮"的观察不矛盾） | ✅ 抄 |
| 触发方式 | 每次查询**自动**落库；SQL 模块"同一 SQL 执行多次→生成单独记录"，**不去重** | ⚠️ 部分抄 → 自动落库 **+ hash 去重** + TTL |
| 历史查询 | 可视化查询页「查询历史」图标，看按数据集的查询历史/日志/状态 | ✅ 抄（R-40） |
| 草稿态 | "临时查询需点保存才入文件夹并重命名" | ✅ 抄（R-41） |
| 清理策略 | 公开文档未说明 | ❌ 不引入后台任务 → **查询时惰性清理** |

### 2.2 业界对照（竞析）

| 产品 | 触发 | key 形态 | 生命周期 / 清理 | 可见性 |
|------|------|----------|-----------------|--------|
| 火山 DataWind | 每次查询**自动** | 自增数字 id | 未公开 | 未公开 |
| Superset permalink | 显式复制 | UUID | `key_value.expires_on` + 每日 prune | 无资源权限则看不到 |
| Metabase `/public/question/<uuid>` | 显式创建 | UUID | 可随时停用 | 任何持链者可看 |
| Grafana snapshot | 显式 Publish | 短 key | 强制选 1h/1d/1w/never | 任何持链者 + 组织列表 |
| Kibana permalink | 显式 Share | saved-object id | ILM 默认永久 | 继承认证 |

**三个结论**：① 业界普遍用**双层**化解自动落库的爆炸（自动只写轻量可 TTL 层，显式才写持久可分享层）；② 清理后旧链普遍**直接失效**并降级报错；③ 无账号体系下"谁能看到"＝**任何持链者**——这也是 id 必须不可猜的原因。

## 三、查询记录契约（R-30 改写 / R-08' 合并）

### 3.1 表结构 `bi_query`（本期唯一新增表）

`query_id PK`（**不可猜 UUID v4**）· `spec_json`（内含 `v` 版本字段）· `spec_hash UNIQUE`（去重键）· `dataset_id` / `chart_id` / `source_type` · `row_count` / `duration_ms` / `ip` · `created_at` / `last_accessed_at` / `hit_count` · **`owner_id` / `tenant_id`（nullable）**。

- **裁定 1（表数）**：本期仅建 **1 张**。语义上"配置资产（upsert 可清理）"与"行为事件（append-only 合规保留）"分离，账号体系落地后再**物理拆** `bi_audit_log`；本期用 `hit_count` / `last_accessed_at` 顶行为事件。
- **裁定 2（owner/tenant）**：**保留** `owner_id` / `tenant_id`（nullable）。理由：R-22 已把"新实体落库即带 owner（nullable、只加字段不加鉴权）"定为**不可逆埋点**（`bi_dataset` / `bi_chart` / `bi_share` 均已按此执行），新表独缺会成为唯一缺口，多租户上线后历史数据无法归属。**（此项推翻了数析"删除"的主张。）**
- **禁止后台清理定时任务**：Data Insights 全仓 `redis|asynq|cron` 零命中，无定时任务基建。

### 3.2 id 与地址栏
- `?q=<uuid>` = **记录寻址**（唯一定位）。
- `?edit=` / `?datasetId=` 保留为**临时编辑上下文**（不落库）。
- 优先级：`q > edit > datasetId`；`q` 存在时忽略其余。

### 3.3 落库触发与去重
**内容 hash 去重 upsert + 异步写入 + 显式动作强制 flush + TTL 惰性清理**。
- 触发：查询执行即写（异步）；"保存 / 分享"等显式动作强制 flush。
- 目标：去重后 ≤1000 行/天、去重率 ≥60%。

**四种策略对比（数析量化，假设 N=50 / 人均建图 5 次/天 / 单次建图 10 次查询 / 唯一配置比 40%）**

| 策略 | 记录量/天 | 复杂度 | 丢"中间态复用"风险 | 对查询 P95 |
|------|-----------|--------|--------------------|------------|
| ① 每次执行落库 | 2500 | 低 | 无 | **高**（同步 +30~80ms，顶破 1.5s） |
| ② **hash 去重 upsert（选定）** | **1000** | 中 | 无 | 中（重复近零成本） |
| ③ 仅显式动作 | 250 | 低 | **高** | 低 |
| ④ debounce 合并 | 250~500 | 高 | 中 | 低但尾延迟不确定 |

### 3.4 TTL 与惰性清理
轻量记录设 TTL，**读时判过期**并惰性清理（无定时任务）；清理后打开走降级（U-10）。

### 3.5 还原流程
打开 `?q=` → 记录命中 → 按 `spec_json.v` 复原 → 校验 dataset / 字段有效性 → 失效走 U-12 降级。

### 3.6 异步写入技术约束（**待工程确认**）
现无 Redis / asynq / cron。方向：**进程内有界队列 + goroutine 异步写 + 显式 flush 兜底**。待确认：① 进程重启的写丢失窗口；② flush 幂等性；③ 异步写与 `database.WithTx` 的事务边界（落库失败是否波及查询响应）；④ `spec_hash` UNIQUE 下并发 upsert 的 `ON CONFLICT DO UPDATE` + `hit_count` 原子自增。

## 四、草稿态与另存为语义（R-41）

| 状态 | 触发 | 行为 |
|------|------|------|
| 新建草稿 | 新查询 | 标「**未保存●**」，不落库 |
| 已落库未改 | 打开旧记录 | 只读引用 |
| 已修改未保存 | 编辑已落库记录 | 标「未保存●」，**不自动覆盖** |
| 更新当前 | 显式更新 | upsert 原 `query_id` |
| 另存为新 | 显式另存 | 生成新 `query_id`，原记录不变 |

> **必须禁止默认覆盖**：否则**已分享出去的链接会被静默改写**，是明确的投诉源（瑞思）。配套提供「更新当前 / 另存为新 / 重命名」。

## 六、层 A / 层 B 与指标

### 6.1 与 `/share/:token` 的关系
- **层 A 记录层（本期）**：`bi_query` + `?q=<uuid>`——不可猜 UUID、**无密码**、随 TTL。

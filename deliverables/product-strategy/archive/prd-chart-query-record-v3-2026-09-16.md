## 📌 TL;DR（执行摘要）

- **机制不变，生命周期变了**：v2 的「TTL 惰性清理 = 删除记录」整体改为「**软过期标记，永不物理删除**」。过期记录从历史列表默认视图隐藏，但**直链仍可打开、条件仍能 100% 完整还原**，仅提示已过期 + 提供「另存为新」。
- **"删除"这个动作从产品里消失**：取消"删除个人历史"，改为「**从我视图中移除**」（浏览器本地标记）。析客把它定为**永久机制**而非临时妥协——任何记录都可能已被分享，真删会断链。
- **全员共享已拍板接受风险**：v2 的隐私缓解（"敏感条件不入公共历史/需显式发布"）**整体废弃**，改为元数据化列表 + 敏感键脱敏 + L0 使用约定；触发重评的条件已写死。
- **不真删的代价可忽略**：按 1000 行/天，1 年 ≈36.5 万行 / 1.1–2.5 GB，3 年 ≈110 万行 / 3.4–7.6 GB（体积为假设）。PG 单表 <1000 万行且 <50 GB 无需干预 → **本期不需要任何归档或清理组件**。
- **主理人修正 3 处**（详见 §3）：① 数析建议的部分索引**根本建不出来**（PG 部分索引谓词必须 IMMUTABLE，`now()` 是 STABLE）；② **TTL 默认 90 天 > 默认视图窗口 30 天 → 默认路径上"过滤过期记录"是空操作**，数析的性能估计偏悲观；③ "最短见价值"应把"分享闭环"与"历史列表可用"拆开算。

## 1. 两项决策的落地解释（含作用范围）

### D-A「先全员共享」
历史查询列表**默认全员可见**，不做"仅本人可见"。`owner_id`/`tenant_id` 字段**保留但退为审计字段**（无值可填，不参与过滤）——与 R-22"新实体落库即带 owner、只加字段不加鉴权"的不可逆埋点原则一致。

### D-B「不应该有真删」
主理人解读（**已向产品负责人标注，如解读偏差需纠正**）：不是禁止 DELETE 语句，而是——
1. **产品语义上任何用户可见的"删除"动作都不存在**；
2. **任何人分享出去的链接，不会因别人的操作或系统清理而失效**。

**作用范围（重要边界）**：产品负责人是在"删除历史"的语境下作答，故范围**限定为查询记录（`bi_query`）**。数据集 / 图表 / 数据源 / 分享（`bi_share`）**当前仍为真删，本次决策不改变它们的语义**。由此产生一个自洽结果：数据集被真删后，查询记录的 `spec_json` 仍自包含，**直链仍能还原条件**，仅结果侧降级（见 U-12）。

## 2. 四件冲突的裁定（析客定稿）

| # | 冲突 | 裁定 | 理由 |
|---|------|------|------|
| C1 | TTL 形态：删除 / 软过期？ | **记录永不物理删除**，仅软过期。判定用 `expires_at` **单字段**（`IS NULL` 或 `> now()` 即未过期），**不新增 `status` 枚举**。过期后：默认视图隐藏、直链可开、条件完整还原、顶部 banner 提示 + 「另存为新」。`hit_count`/`last_accessed_at` **仍更新**（访问客观发生、零额外成本）；`expires_at` **打开时不刷新**（仅创建时写入，默认 created_at+90 天，NULL = 永久） | 状态是 `expires_at` 的派生值，重复存储会与之漂移 |
| C2 | "删除个人历史"如何处置？ | 取消删除，改「**从我视图中移除**」（localStorage 记 query_id，仅本机、仅本人隐藏）。定位为**永久机制**（账号落地后仍是 UX 主路径）。未来若遇"彻底抹除"的合规诉求 → 走**脱敏重写**（清空敏感条件值、保留行与 query_id），**不删行** | 无账号体系下 `owner_id` 无值可填；且任何记录都可能已被分享，真删会断链 |
| C3 | 全员共享后的隐私缓解（重写 v2 §6） | ① 历史列表**只展示元数据**（数据集名/时间/行数/耗时），**不展示条件值明细**——看明细须打开记录；② 已知敏感键（客户 ID/手机号）的筛选值**截断或中段脱敏**；③ 依赖 L0 内网 + 使用约定"勿把 PII 写入筛选条件" | v2 的"需显式发布才可见"与 D-A 直接矛盾，整体废弃 |
| C4 | 不真删的存储控制 | 单条 `spec_json` **上限 32KB**，超限**拒存**并友好提示；历史**默认视图过滤已过期**记录 = 软归档。演进方向（本期不做）：大体积 spec 迁冷表 + 敏感值不可逆脱敏，保留 query_id 与直链 | 表单调增长需要一条硬上限兜底 |

## 3. 主理人一致性修正（3 处，其中 1 处为技术硬伤）

### 🔴 修正 1（技术硬伤）：数析建议的部分索引**建不出来**
数析要求"部分索引 `(created_at DESC) WHERE status='active'`（过期记录走直链，不进默认视图）"。两处问题：
- 与 C1 冲突——析客已裁定**不加 `status` 字段**；
- **即便改用 `expires_at`，也建不出来**：PostgreSQL 的**部分索引谓词必须是 IMMUTABLE 函数**，而 `now()` 是 STABLE。写成 `WHERE expires_at IS NULL OR expires_at > now()` 会被 PG 直接拒绝：`ERROR: functions in index predicate must be marked IMMUTABLE`。

**裁定**：**放弃部分索引**。改用普通复合索引 `(created_at DESC, query_id)`，把过期判定作为索引扫描**之后的 filter 谓词**。影响：查询不能做成 index-only scan，但因为默认视图带 `LIMIT`（keyset 分页），索引扫描可提前停止，代价可控（详见修正 2 后进一步下降）。

### 🟡 修正 2（设计矛盾）：默认参数下"过滤过期记录"是**空操作**
析客定 **TTL 默认 = created_at + 90 天**；数析定 **默认视图窗口 = 最近 30 天**。因为 **90 > 30**，默认视图内的记录**永远不可能过期**——"默认视图过滤过期记录"这条在默认参数下**命中零条**。

含义：
1. 数析基于"×50 放大 + 需过滤过期"给出的性能风险**偏悲观**；默认路径上不存在过期项，`首屏 P95 ≤400ms` 的把握比其估计更高。
2. 但过滤逻辑**仍必须实现**——用户切换到"全部/更早时间范围"或 TTL 被调短时就会命中。
3. **新增一条配置约束**：`TTL 下限 ≥ 默认视图窗口`（否则默认视图会开始出现过期项，且性能假设失效）。建议在配置层做校验。

### 🟢 修正 3（度量口径）：拆分"最短见价值"
路径把 R-44（分页 + 索引）算进"最短见价值"，理由是"×50 规模下无分页列表不可用"。但**历史列表不是"分享"的前置**——用户的核心诉求是"复制地址栏分享出去"。故拆为两个度量：
- **分享闭环**：`G1 → R-08' → R-30' → R-31'` = **18–29 人日**（不含 R-44）
- **历史列表可用**：+ R-40（4–7）+ R-44（2–3）= **24–39 人日**

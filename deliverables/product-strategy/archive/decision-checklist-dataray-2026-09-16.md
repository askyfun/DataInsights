## 一、必须先答（阻塞接口契约，不答即停工）

### D1｜度量级表达式的形态 —— 决定 `bi_metric` 表结构与 `/api/metrics` 契约

| 选项 | 说明 | 代价 |
|------|------|------|
| **A 类型枚举 + 表达式兜底（推荐）** | `metric_type ∈ {simple, ratio, percent_of_previous, running_total, percent_of_total}`；`simple` 走现有 `field + agg`，其余走 `expr` 兜底 | 表结构多一列、校验器需分层；换来可校验、可 certified、UI 能给模板 |
| B 纯自由文本表达式 | 最灵活，任意口径都能写 | 校验面变大、UI 无引导、无法 certified；错误只能靠 R-20 事后兜 |
| C 纯枚举（无自由文本） | 最安全，白名单化 | `sum(a)/sum(b)` 之外的复合口径做不了，后续必然二次返工 |

> 影响面：`bi_metric` DDL、`/api/metrics` CRUD 契约、`QuerySpec.metric_refs`、`query/ast.go` 的 `ApplyMetricMappings`、前端 `Metrics.tsx` 与表达式编辑器（R-19）复用面。

### D2｜首期支持的数据源 / 方言范围 —— 决定 R-06 是否拆期

现状：已实现 4 个驱动 —— PostgreSQL、MySQL、ClickHouse、StarRocks。

| 选项 | 说明 |
|------|------|
| **A 先 PG + MySQL 全能力，CH/SR 仅 `simple`/`ratio`（推荐）** | 窗口函数（`running_total`/`percent_of_previous`）先在 PG/MySQL 落地；CH/SR 探针通过后再补 |
| B 四种全支持 **—— 已选** | 需先跑窗口函数方言探针确认 CH/SR 可用，R-06 工期顺延；探针不通过则需二次决策（降级发货 or 顺延） |
| C 仅 PostgreSQL | 最快，但 MySQL 是常见生产库，易被用户当成能力缺失 |

> 注：无论选哪个，**探针都要跑**（工程立即执行）；你的决策决定的是"探针不通过时是否降级发货"。

### D3｜看板全局筛选模型 —— 决定 `bi_dashboard.global_filters` 结构与 render 契约

| 选项 | 说明 | 代价 |
|------|------|------|
| **A Metabase 式：控件 → 卡片列映射 + 自动连接含同字段的其它卡片 + 默认值（推荐）** | 模型简单，用户心智自然 | 跨图表"作用域"能力弱于 Superset |
| B Superset 式 scope / DataMask | 支持一张筛选控件精确作用于一组图表 ID | jsonb 结构与前端状态机复杂，工期约 +30% |

> 影响面：`bi_dashboard.global_filters` jsonb、`/api/dashboards/{id}/render` 契约、R-25 filter-state 与 R-05 联动级联的抽象层。

## 二、边界裁定（开工后一周内答清，不阻塞第一批）

### D4｜受控导出是否进本期
- **A（推荐）不进本期 —— 已选**：放 Phase 2，前提是 R-08 留痕已上线（导出必须留痕，否则等于开了后门）。
- B 进本期：+5–7 人日（限行 2000/10000 + 限字段 + 必留痕）。

### D5｜虚拟字段能否引用虚拟字段（嵌套）
- **A（推荐）允许 + 循环检测**：与 Metabase custom column 心智一致；须在 T-02 引用校验里加自引用/循环检测。
- B 禁止嵌套：只允许引用物理列 / SQL 数据集输出列，实现最省但用户会当场发现"写不了"。

### D6｜表达式作用域边界
- **A（推荐）仅本数据集字段（含虚拟字段）**：禁子查询、禁跨数据集、**禁在 expr 里写聚合**（聚合属指标层职责，避免与 D1 职责重叠）。
- B 允许 expr 内写聚合：能力更强，但与指标层形成两套并行的聚合口径，后期口径治理会打架。

> 现状依据：数据集模型没有 join 能力（`bi_dataset` 只有 `query_type ∈ {table, sql}` + `query_sql` + `columns`），故"跨数据集引用"在本期无实现基础。

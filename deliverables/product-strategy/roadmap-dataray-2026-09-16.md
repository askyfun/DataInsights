## 📌 TL;DR

- **进度真相**：v3.1 里「未做」的**图型扩展轨 Batch 0/1/2 已基本落地**——实测图型从 **7 种 → 13 种**（+柱横条/饼环形/堆叠等变体），聚合从 5 种 → **7 种**（新增 `count_distinct`、`median`），**已越过原定「净增 5 种」的断点**。
- **但主线一根没动**：`/api/queries` **实测 404**（curl 打本机 23352 确认）、G1 校验器目录不存在、`?q=` 前端零命中。**「能画图」和「能分享」之间仍然断着**，这是当前第一优先级，不是图型。
- **一项不可逆欠账已拖 3 天**：`bi_datasource/bi_dataset/bi_chart/bi_share` 四表的 `owner_id`/`tenant_id` **仍未落库**（实测 `model/query.go` 是唯一带这两列的模型）。**Phase A 必须还掉**，越晚补存量数据越难归属。
- **竞品结论（25 家）**：① **免登录分享已是行业标配不是差异点**（开源 5 家 + 国内 6 家全有）；② 但**「密码 + 过期」稀缺**——Superset/Metabase/Grafana/Redash/Lightdash **全部无密码**，这是 DataRay 正确且稀缺的组合；③ **最贴身对手是 DataEase**（同 ECharts 栈、Apache-2.0、分享机制是我们**超集**：有效期+密码+自定义后缀+Ticket 参数绑定）。
- **最硬的战略事实**：AI 问数的准确率杠杆**不是模型而是语义层**——裸 text-to-SQL 在企业真实 schema 上 **52.4%/21.3%**，接上语义层后跳到 **84.5%/98.2–100%**。→ **语义层（R-06）是 AI 的前置，不可跳过**；反过来，**先做 AI 再做语义层等于把钱花在错的一端**。
- **AI 切入点裁定**：最佳 = **画布内的自然语言局部改写**（换维度/换图型/加筛选/改排序），失败可撤销，把「正确性问题」降级为「交互问题」；最差 = **一句话生成整套看板 / 全局 Chat BI / 自主多步 agent**（前置条件恰好是你全没有的账号+权限+指标治理）。
- **四阶段**：**A 收口**（2026 Q4）→ **B 可信消费**（2027 Q1，看板+语义层）→ **C 组织化**（2027 Q2，账号/RBAC/RLS/多租户）→ **D 智能与分发**（2027 Q3，AI 出图+嵌入）。
- **Phase C 不是拍脑袋**：它是 decision-log 里早已写死的**打破条件被触发后的应对**（出现账号体系 / 网络越出内网 / 接入跨团队外部用户 / 出现实际投诉——任一成立即失效重评）。
- **规模**：Phase A **≈53–90 人日**；A–D 全量 **≈225–365 人日**（估算）。**最短见价值** 仍是分享闭环剩余 **≈8–14 人日**。

## 2. 产品定位（第二轮竞品调研结论 · 25 家 / 三阵营）

> 完整取证（含每条的来源域名与信息时间）见 `competitive-analysis-...-2026-09-16.md` 的「第二轮竞品调研」章节。

### 2.1 三阵营形势

| 阵营 | 代表 | 对本项目的核心含义 |
|------|------|--------------------|
| **开源 / 自托管** | Superset · Metabase · Redash · Grafana · Lightdash · Evidence · Rill · Cube · **DataEase** | 免登录分享是**标配**；**密码保护普遍缺失**（5 家无密码）；**MCP 成为 2026 最低 AI 门槛**（Metabase v60 / Superset 6.0 / Cube / Rill 全有） |
| **国内商业 BI** | 火山 DataWind · 帆软 FineBI · 观远 · Quick BI · 腾讯云 BI · 网易有数 · Smartbi · 永洪 · 衡石 · DataFocus · Sugar BI | 免登录分享同样标配（6 家全有，5 家带密码+有效期）；**普遍缺「分享链接统一管理 / 一键失效」**；AI 问数**名不副实**（需先做指标治理） |
| **国际巨头 + AI 原生** | Tableau · Power BI · Looker · Qlik · Sigma · ThoughtSpot · Wren AI · Vanna · Hex · Omni | Gartner MQ 2026（2026-06-29）把 **Agentic Insights / Conversational Analytics / Semantic Modeling 列为必备能力**；**六强 AI 全部长在自家语义层上**；AI 计费全面转向**按提问数 / token 计量** |

### 2.2 三栏结论

**A. 该抄的（table-stakes）**

| # | 项 | 证据 |
|---|----|------|
| 1 | **分享链接「撤销即永久失效 + 轮换」** | Metabase：关闭公共链接后重新分享会生成**不同**链接、旧链接**永久失效**（metabase.com/learn，2026-05）。DataRay 已有密码+过期，缺**轮换与吊销**语义 |
| 2 | **分享链接统一管理清单 + 一键失效** | 网易有数可在项目中心统一管理分享链接有效性；Quick BI 有「不再公开」；永洪有取消分享。**国内厂商普遍缺、DataRay 也缺** |
| 3 | **「任一改动即时出图」，中间没有 Run 割裂** | Metabase 被评为拖拽摩擦度**第一**，凭此点结构性胜出 Superset（superset 需先选图型再配置、很多视图要 Run 才见结果）。DataRay **已有自动查询 effect**，属既有优势，须守住 |
| 4 | **过期默认值不设为「永久」** | FineBI 公共链接**默认永久有效**、Smartbi 自动生成**4 位密码**、永洪密码仅 **1–8 位**——都是被吐槽的妥协 |
| 5 | **至少接一个 MCP server** | Metabase v60 官方 MCP（2026-05）· Superset 6.0 MCP（2025-12）· Cube 原生（2025-06）· Rill（2026 初）。**成本远低于自研 NL2SQL** |
| 6 | **「快照即真相」——不可变快照分享** | 反向定位点：所有人都在卖「定义一次、到处一致」，**没人卖「这张图当时的数据长什么样」**。`bi_query` 永不删 + UUID 寻址正是天然底座 |

**B. 不该抄的（对 L0 单团队内网是过度设计）**

| # | 项 | 反证 |
|---|----|------|
| 1 | **多租户 / 行列级 RLS / SSO / SCIM** | 在 Metabase 全压到 Pro（$575/mo）+ Enterprise（$20k/yr）；Lightdash 的 SAML/SCIM 为 Enterprise-only。**单团队内网无收益，且显著抬高查询链路复杂度** |
| 2 | **独立语义层 / metrics-as-code（重型形态）** | Cube 的代价：手写 YAML/JS + pre-aggregation 是「ongoing discipline」+ 单模型只解析单一数据源。**反证：DataEase 靠「数据集 + 视图级计算字段」的弱语义层就在中小企业跑通了**。→ DataRay 只需**最小语义层**（见 Phase B），不是 Cube 那套 |
| 3 | **数据大屏 / 像素级 Canvas 布局** | Grafana 12.2 重做 Canvas pan/zoom、DataEase 200+ 大屏模板。属「展示」需求，与「分析」主干正交，**会稀释拖拽建图的投入** |
| 4 | **定时调度与订阅** | Lightdash 自托管实现 scheduled delivery 要额外拉 **browserless(Chromium) + SMTP + S3** 三件套。对本项目 ROI 为负，且违反「不引入后台定时任务」红线 |
| 5 | **BI-as-code 路线（Evidence / Rill）** | 目标用户是会 SQL + Git 的工程师；Evidence 明确是 **publishing 而非 exploration** 模型——与「拖拽给非技术人自问」定位**正交甚至相反** |
| 6 | **pre-aggregation / 缓存引擎** | Cube CubeStore 换到 sub-50ms，代价是持续运营调优 + CCU 计费不可预测。DataRay 直连四方言即可，缓存后置 |

**C. 反向定位机会**

| # | 机会 | 论证 |
|---|------|------|
| 1 | **「内网也按最小暴露原则分享」** | 反例有实证：Redash 的 `public_url_token` 无密码无过期，生产复盘记录过**跨组织数据泄露**；Metabase 官方明确警告公共链接「不能靠 filter 藏数据」。**本阵营仅 DataEase 与国内少数几家有密码** → DataRay 的「密码+过期」组合正确且稀缺，应直接写进产品叙事 |
| 2 | **把 AI 放进免费自托管** | Lightdash/Evidence 把 AI 锁在商业云档；**Metabase 反其道行之**（v60 全套餐开源 + 支持 BYO Anthropic key），官方理由：「用户想要 AI 就会绕过你，把数据贴进 ChatGPT」 |
| 3 | **零依赖 / 零运维** | Superset 匿名分享要同时命中 4 项配置 + `superset init` + 手工授 6 类权限；guest token 还要 JWT secret + CORS + SameSite 全对齐，社区大量「嵌入面板闪一下被踢回登录页」。Lightdash 绝对依赖 dbt、Cube 语义模型不可视化。→ **Go 单二进制 + 四方言直连 + 不锁建模工具**是可打的牌 |
| 4 | **免登录的人也能问一句** | ThoughtSpot Pro 限 **25 次 Spotter/人/月**、Qlik 免费档仅 25 次提问——**小团队根本买不起**。巨头因定价结构**无法**跟进这个位置 |

### 2.3 两个必须盯住的对手

- **DataEase（最贴身）**：同为 ECharts 技术栈、Apache-2.0 开源、拖拽 BI、目标客户高度重叠。**它的分享机制是 DataRay 的超集**——公共链接支持**有效期 + 密码 + 自定义后缀（8–16 位）+ Ticket 机制**（单资源多 token、参数绑定如 `{"国家":"Lebanon"}`、每 ticket 独立有效期、可设「必选」）。2025-09-16 的 v2.10.13 LTS 引入 **SQLBot 智能问数**。→ **DataRay 无法在分享机制上取胜，差异化只能落在「问题导向 vs 大屏导向」与「零配置」上。**
- **Metabase（体验标杆）**：拖拽→即时出图摩擦度第一；v60（2026-05）「AI just went open source」把 AI 下放所有套餐 + 官方 MCP server。**它是 DataRay 在交互体验上的对标对象，也是 AI 落地姿势的参照。**

### 2.4 关键战略事实：AI 的杠杆是语义层，不是模型

| 数据 | 值 | 来源 |
|------|-----|------|
| 裸 text-to-SQL 在企业真实 schema（Spider 2.0） | **21.3%** | 二手转述，2026 |
| 同一 agent 在 Spider 1.0 / 2.0 | 91.2% → **21.3%** | 同上 |
| BIRD 基准：裸 text-to-SQL → 带 Ontology 语义层 | 52.4% → **84.5%** | Databricks Genie，2026-06，二手 |
| dbt Labs 基准：语义层前后 | 90.0% → **98.2%**；84.1% → **100%** | 2026-04，二手 |
| BIRD-Interact 多轮对话任务最好成绩 | **≈16%** | 二手 |
| Cortex Sense 把结构化上下文任务准确率 | 24% → **86%** | Snowflake，2026-06，二手 |

> ⚠️ 上述均为**二手转述**，不可作为承诺性指标引用。但方向一致性极强（6 组独立数据同向），**足以支撑一条排期判断：语义层必须先于 AI 问数**。

## 3. 中长期阶段划分

**R-70 的边界（先写死，防止范围蔓延）**：

## 7. 风险栏

| 风险 | 状态 | 说明 / 阈值 |
|------|------|------------|
| **异步落库在进程崩溃时丢记录** | 🔴 **未消除** | 进程内队列 → SIGKILL 时未落盘记录丢失。缓解：显式动作前 `Flush`、队列满同步兜底。**根治需 WAL / 本地持久队列，超出本期范围** |
| **AI 出图的 prompt 注入面**（新增·Phase D） | 🟠 **须前置设计** | NL 输入是**新的可构造查询入口**，必须与 `?q=` 同级别对待：经同一套 G1/G2 Guard，**不得绕过**。参照：Superset 6.0 的 MCP `execute_sql` 工具在 2025-12 爆出 **RLS 未生效漏洞**并紧急修复——**AI 通路是新攻击面，不是免检通道** |
| **AI 生成 spec 污染查询记录表**（新增·Phase D） | 🟠 **须前置设计** | 若 AI 生成的配置也走「自动落库」，`bi_query` 会被大量一次性/错误配置灌满，**稀释去重率与历史列表信噪比**。需在契约里预先裁定：AI 结果默认**不落库**，仅在用户显式「另存为」后落库 |
| **无鉴权 + 全员共享 → 全库查询条件可被任意浏览** | 🟡 **已接受** | 产品负责人明确接受。**打破条件**：① 出现账号/多租户体系 ② 网络越出内网 ③ 接入跨团队或外部用户 ④ 出现实际投诉——**任一成立即失效**，对应 **Phase C** |
| **分享链接不可吊销**（新增） | 🟠 **table-stakes 缺口** | 竞品普遍提供「关闭分享 / 一键失效」（Metabase 撤销后旧链接永久失效、网易有数项目中心统一管理）。DataRay 现状：无吊销入口、无分享清单。缓解：不真删 + 过期时间已部分对冲 |
| **`owner_id` 有字段无值** | 🟡 半消解 | 全员共享后 `owner_id` 退为审计字段。既有 4 表埋点**仍欠账（不可逆）** |
| **Phase C 会摧毁免登录分享的差异化** | 🟡 **须知情** | 引入账号体系后 `?q=` 匿名直链必然退化为「管理员开关 + 合规补丁」。→ **A/B 阶段要快**，差异化窗口只在无鉴权阶段存在 |
| **引入 Redis / worker 破坏「轻部署」叙事** | 🟡 待评估 | Phase C 的 R-09 缓存与 Phase D 的调度都可能引入外部基建。若引入，须同步重估「Go 单二进制」这一核心卖点是否还成立 |
| **`bi_query` 表单调增长** | 🟢 已证伪 | 1 年 ≈36.5 万行 / 1.1–2.5 GB；3 年 ≈110 万行 / 3.4–7.6 GB。PG 单表 <1000 万行且 <50 GB 无需干预 |
| **真库端到端验证** | 🟢 **部分消解** | 迁移 `00001→00003` 已在真实 PG 应用（`192.168.10.70/insight_dev`）。残留：软删除的**功能级行为**无真实数据可验，待造数据补验 |
| **AI 准确率被高估** | 🟠 **须知情** | 裸 text-to-SQL 在真实企业 schema **21.3%**、多轮对话任务 **≈16%**（均二手）。这是 R-70 必须限定为「局部改写」而不是「自主生成」的**量化依据** |
| **编号纪律** | 🟡 已登记 | R-49 保留编号作废留空**不回填**；R-69~R-71 本轮新增；**派活前必须 grep 现有编号最大值**（已四度踩坑） |
| **竞品情报的二手误差** | 🟡 已登记 | 2025–2026 大量对比文宣称 Redash「已消失/停更」，事实是它按月在发版（v25.01 / v25.08 / v26.03）。→ **竞品事实一律以官方文档 + GitHub release 为准** |
